# WALL-E 项目当前实现说明

## 1. 项目概述

这是一个基于 **PlatformIO + Arduino** 的 WALL-E 小车/机器人项目。

当前主线实现已经从“简单按距离调速”升级为：

- **两轮差速动作抽象**
- **多阶段避障状态机**
- **MPU6050 偏航积分与直行修正**
- **舵机多方向扫描决策**
- **WS2812 风险指示**
- **串口状态上报**

当前仓库中主要包含两条实现线：

1. **当前主实现**：`src/main.cpp`
   - 目标板：**Arduino Uno**
   - 当前已实现：扫描避障、差速运动控制、偏航修正、状态机调度、灯光与串口反馈

2. **预留扩展实现**：`src/esp32_main.cpp`
   - 目标板：**ESP32-CAM**
   - 当前仅保留最小启动框架，尚未接入视觉能力

此外，`lib/srcv4/` 中仍保留 ELEGOO Smart Robot Car V4.0 的历史参考代码，但它**不是当前 Uno 主程序的运行主链路**。

## 3. 构建目标说明

`platformio.ini` 中配置了两个环境：

- `env:uno`
  - 默认环境
  - 编译 `src/main.cpp`
  - 排除 `src/esp32_main.cpp`

  - 编译 `src/esp32_main.cpp`
  - 排除 `src/main.cpp`

因此，**当前真正完整且可运行解释的主程序是 Uno 版本**。

## 4. 当前主程序的核心变化

相较于之前的“单次测距 + 直接调速”版本，当前 `src/main.cpp` 的核心已经变为：

1. **统一动作抽象**
   - 使用 `MotionCommand` 表达 `停止 / 前进 / 后退 / 左转 / 右转`

2. **避障过程状态化**
   - 使用 `AvoidancePhase` 表达“前进、右扫、中扫、左扫、决策、后退、转向”等阶段

3. **偏航闭环控制接入**
   - 使用 MPU6050 的 Z 轴角速度积分得到 `yawDeg`
   - 在直行/后退阶段对左右轮输出进行差速修正

4. **扫描结果显式保存**
   - 记录 `scanRightDistanceCm / scanCenterDistanceCm / scanLeftDistanceCm`
   - 决策时不是只看当前一次测距，而是使用完整扫描结果

这说明当前版本已经从“简化避障原型”进化为：

> **一个具备方向扫描、状态决策与偏航修正能力的基础自主移动底盘。**

## 5. 系统总体结构

当前 `src/main.cpp` 的核心仍然是：

- 一个共享状态：`RobotState`
- 四个周期任务：
  - `servoSensorCallback()`
  - `motorControlCallback()`
  - `ledControlCallback()`
  - `serialReportCallback()`

整体结构可以理解为：

```/dev/null/architecture.md#L1-17
感知层：
  舵机位置
  超声波测距
  MPU6050 姿态/温度

↓ 写入

共享状态层：
  RobotState

↓ 被读取

执行与反馈层：
  电机控制任务
  LED 任务
  串口上报任务
```

这是一种典型的**协作式定时任务 + 共享状态驱动架构**。

## 7. 共享状态 `RobotState` 的职责

当前版本的 `RobotState` 已经不是简单的数据缓存，而是整个系统的“运行上下文”。

它主要包含以下几类信息：

### 7.1 舵机相关

- 当前角度 `servoAngle`
- 目标角度 `servoTargetAngle`
- 上次发出舵机命令时间 `lastServoCommandMs`

作用：

- 支撑“目标角度 -> 等待稳定 -> 再采样”的扫描流程

### 7.2 超声波相关

- 当前测距 `distanceCm`
- 前向距离 `frontDistanceCm`
- 回波时间 `pingTimeUs`
- 右/中/左三方向扫描结果：
  - `scanRightDistanceCm`
  - `scanCenterDistanceCm`
  - `scanLeftDistanceCm`

作用：

- 不只保存当前一帧数据，还保存完整一次避障扫描的结果

### 7.3 MPU6050 相关

- 加速度、角速度原始字段
- 温度 `temp`
- 积分偏航角 `yawDeg`
- 目标航向 `headingTargetDeg`
- 陀螺零偏 `gyroBiasZ`
- 偏航修正量 `headingCorrection`
- `mpuReady` 状态标志

作用：

- 支撑偏航估计、目标航向锁定、直行修正

### 7.4 电机输出相关

- 左右轮速度
- 左右轮方向
- 当前动作命令 `motionCommand`

作用：

- 让串口日志和控制执行共享同一份输出状态

### 7.5 避障状态机相关

- 当前阶段 `avoidancePhase`
- 阶段开始时间 `phaseStartedMs`
- 当前阶段计划持续时间 `phaseDurationMs`

作用：

- 让“后退一段时间、原地转向一段时间”这类动作具备明确时序

## 8. 两轮差速动作抽象

当前版本把底盘动作抽象成了一个统一枚举 `MotionCommand`：

- `MOTION_STOP`
- `MOTION_FORWARD`
- `MOTION_BACKWARD`
- `MOTION_TURN_LEFT`
- `MOTION_TURN_RIGHT`

这层抽象的意义非常大，因为它把：

- 高层决策
- 左右轮方向
- 左右轮速度
- 偏航修正

统一收敛到了 `applyMotion()` 里处理。

### 8.1 抽象前的典型问题

如果不做动作抽象，代码通常会出现：

- 到处直接写左右轮引脚
- 左右轮速度分散在各个条件分支里
- 偏航修正难以集中管理
- 后续新增动作时容易重复

### 8.2 当前抽象后的优点

现在的结构变成：

1. 状态机只负责决定“要做什么动作”
2. `applyMotion()` 负责把动作翻译成左右轮输出
3. `setMotorOutput()` 负责把单轮输出落到引脚

这样就形成了三层职责分离：

```/dev/null/motion_layers.md#L1-9
决策层：
  我要前进 / 后退 / 左转 / 右转 / 停车

动作层：
  applyMotion()

驱动层：
  setMotorOutput()
```

### 8.3 差速动作映射关系

当前动作映射逻辑可以概括为：

| 动作 | 左轮方向 | 右轮方向 | 说明 |
|---|---|---|---|
| 停止 | 停 | 停 | 两轮 PWM 为 0 |
| 前进 | 前 | 前 | 支持偏航修正 |
| 后退 | 后 | 后 | 支持偏航修正 |
| 左转 | 后 | 前 | 原地左转 |
| 右转 | 前 | 后 | 原地右转 |

这套映射非常符合两轮差速底盘的基本控制方式。

## 9. 偏航修正逻辑

当前项目已经正式接入了 MPU6050 的偏航修正链路。

## 9.1 数据来源

程序读取 MPU6050 的陀螺仪 Z 轴角速度：

- 原始值单位近似为 `rad/s`
- 扣除启动校准得到的零偏 `gyroBiasZ`
- 转换为 `deg/s`
- 设定死区 `GYRO_Z_DEADBAND_DPS`

这样可以减小静止噪声和零漂影响。

## 9.2 偏航角估计

程序通过时间积分更新：

- `yawDeg += gyroZ * dt`

同时将角度限制在 `[-180°, 180°]` 范围内。

这不是完整姿态融合，但对于：

- 短时直行修正
- 短时倒车修正
- 转向后重新捕获航向目标

已经足够实用。

## 9.3 目标航向的捕获

程序使用 `captureHeadingTarget()` 记录当前的 `yawDeg` 作为目标方向。

这个动作会在以下场景触发：

- 从其他动作切入 `前进`
- 从其他动作切入 `后退`
- 转向完成后恢复前进前
- 决策判定“中间可通、继续前进”时

也就是说，系统不是一直拿“上电时方向”做参考，而是：

> **每次进入一段新的直线运动时，重新把当前姿态作为目标航向。**

这样更符合实际避障过程。

## 9.4 修正作用范围

当前版本的设计是：

- **只在 `MOTION_FORWARD` 和 `MOTION_BACKWARD` 时启用偏航修正**
- **在 `MOTION_TURN_LEFT` 和 `MOTION_TURN_RIGHT` 时禁用偏航修正**

这是合理的，因为：

1. 转向动作本身就是主动改变航向
2. 如果转向时还叠加“保持原航向”的修正，会产生控制冲突
3. 偏航修正更适合服务于“希望走直线”的阶段

因此，这一版的偏航修正作用范围是清晰且正确的。

## 10. 避障状态机设计

当前版本最关键的升级，是把避障过程拆成了显式状态机。

状态枚举 `AvoidancePhase` 包括：

- `AVOID_DRIVE_FORWARD`
- `AVOID_SCAN_RIGHT`
- `AVOID_SCAN_CENTER`
- `AVOID_SCAN_LEFT`
- `AVOID_DECIDE`
- `AVOID_REVERSE`
- `AVOID_TURN_LEFT`
- `AVOID_TURN_RIGHT`

这意味着避障流程已经不再是“一次 if/else 决策”，而是一个具备阶段记忆的执行序列。

---

## 11. 避障状态机完整流程说明

### 11.1 `AVOID_DRIVE_FORWARD`

系统默认处于前进巡航阶段：

- 舵机保持中位
- 按前向距离计算巡航速度
- 调用 `applyMotion(MOTION_FORWARD, ..., true)`

如果前方距离小于等于扫描阈值 `OBSTACLE_SCAN_THRESHOLD`，则：

1. 先停车
2. 清空上一轮扫描结果
3. 状态切换到 `AVOID_SCAN_RIGHT`
4. 舵机转到右侧扫描位

这是完整避障动作的入口。

### 11.2 `AVOID_SCAN_RIGHT`

系统保持停车，等待舵机稳定。

稳定后：

- 记录右侧距离 `scanRightDistanceCm`
- 切到 `AVOID_SCAN_CENTER`
- 舵机回中位

### 11.3 `AVOID_SCAN_CENTER`

系统继续停车并等待舵机稳定。

稳定后：

- 记录中间距离 `scanCenterDistanceCm`
- 同时更新 `frontDistanceCm`
- 切到 `AVOID_SCAN_LEFT`
- 舵机转向左扫描位

### 11.4 `AVOID_SCAN_LEFT`

系统继续停车并等待舵机稳定。

稳定后：

- 记录左侧距离 `scanLeftDistanceCm`
- 切到 `AVOID_DECIDE`
- 舵机回中位

### 11.5 `AVOID_DECIDE`

系统在中位停车，等待舵机再次稳定后进行决策。

当前决策优先级是：

1. **右边可通** -> 右转
2. **中间可通** -> 直接恢复前进
3. **左边可通** -> 左转
4. **都不可通** -> 先后退

这个策略的特点是：

- 明确优先选择单侧通路
- 保留“中间重新通畅则继续前进”的机会
- 在三方向都受阻时进入脱困动作

### 11.6 `AVOID_REVERSE`

系统执行后退动作：

- `applyMotion(MOTION_BACKWARD, MOTOR_TURN_SPEED, true)`

并持续固定时长 `AVOID_REVERSE_DURATION_MS`。

时间到后：

- 自动切换到 `AVOID_TURN_RIGHT`
- 执行一个更长的转向脱困动作

### 11.7 `AVOID_TURN_LEFT` / `AVOID_TURN_RIGHT`

系统执行原地转向：

- 左转：左轮后退，右轮前进
- 右转：左轮前进，右轮后退

转向持续固定时长后：

1. 重新捕获当前航向目标
2. 回到 `AVOID_DRIVE_FORWARD`

这使得“转完以后继续走直线”可以无缝衔接。

## 12. 为什么说当前避障状态机是完整的

从工程角度看，一个“完整”的避障状态机，至少应满足：

1. **有正常巡航入口**
2. **有障碍触发条件**
3. **有扫描阶段**
4. **有决策阶段**
5. **有失败兜底动作**
6. **有从转向/后退恢复到巡航的出口**

当前实现已经具备以上全部环节：

- 入口：`AVOID_DRIVE_FORWARD`
- 触发：前向距离阈值
- 扫描：右 -> 中 -> 左
- 决策：`AVOID_DECIDE`
- 兜底：`AVOID_REVERSE`
- 恢复：转向结束后回到 `AVOID_DRIVE_FORWARD`

因此，这一版已经可以被认定为：

> **完整的、可持续循环运行的基础避障状态机。**

---

## 13. 舵机扫描策略说明

当前舵机不再持续来回摆扫，而是服务于状态机：

- 正常前进时保持中位
- 进入避障时按固定顺序扫描：
  - 右
  - 中
  - 左
  - 回中

这种设计比“持续摆扫 + 取当前值控制”更适合做动作决策，因为它具备两个优势：

1. **扫描结果有明确语义**
   - 知道哪一个值对应右/中/左

2. **采样时机可控**
   - 必须等舵机稳定后再读取测距

这会让决策更稳定，也更容易调试。

## 14. 距离与速度控制逻辑

除了避障状态机，当前版本还保留了巡航调速逻辑。

### 14.1 安全距离区间

- `DIST_SAFE_THRESHOLD = 75cm`
- `DIST_DANGER_THRESHOLD = 7.5cm`
- `OBSTACLE_SCAN_THRESHOLD = 20cm`

其中要注意：

- `DIST_SAFE_THRESHOLD` 主要服务于巡航速度和 LED 风险显示
- `OBSTACLE_SCAN_THRESHOLD` 才是触发扫描避障的关键阈值

### 14.2 巡航调速

在 `AVOID_DRIVE_FORWARD` 阶段：

- 若前方很远，速度接近 `MOTOR_SPEED_MAX`
- 若前方逐渐接近障碍，但尚未达到扫描阈值，则线性减速
- 若进入扫描阈值内，则切换到避障流程

这使得系统具备：

- 平稳接近
- 而不是总在“全速 / 突停”之间跳变

## 15. LED 风险提示逻辑

`ledControlCallback()` 当前以 `frontDistanceCm` 为依据显示颜色：

- 安全区：绿色
- 危险区：红色
- 中间区：使用 HSV 做渐变

这部分的价值在于：

- 直观显示当前前向空间风险
- 便于线下调试阈值
- 不受避障状态机内部细节影响

也就是说，LED 表示的是：

> **“当前前方是否危险”**

而不是“当前处于什么状态机阶段”。

## 16. 串口上报字段说明

当前串口日志已经明显增强，会上报：

- `F`：前向距离
- `C`：当前测距
- `Y`：偏航角
- `HC`：航向修正量
- `P`：避障阶段
- `SR`：右扫描距离
- `SC`：中扫描距离
- `SL`：左扫描距离
- `ML / MR`：左右轮速度
- `FL / FR`：左右轮方向

这比旧版更适合调试，因为它已经能直接观察：

1. 当前是否进入避障状态机
2. 三方向扫描结果分别是多少
3. 偏航角是否在积累
4. 修正量是否只在直行/后退时生效
5. 左右轮输出是否符合动作预期

## 17. 当前版本相对上一版的提升

这一版相比“第一版重构”有几个关键升级：

### 17.1 从单点测距控制升级为多方向决策

之前更像：

- 看当前距离
- 距离近就减速或转向

现在则变成：

- 检测到障碍
- 扫描右中左
- 保存结果
- 决策可通方向
- 再执行动作

这是本质性升级。

### 17.2 从直接控轮升级为动作抽象

之前容易在不同逻辑里重复写电机输出。

现在已经统一为：

- 状态机决定动作
- `applyMotion()` 负责翻译为左右轮输出

更利于维护和扩展。

### 17.3 从传感器接入升级为闭环控制接入

MPU6050 不再只是“挂在系统里”，而是已经真正参与：

- 偏航积分
- 目标航向锁定
- 前进/后退的左右轮修正

这代表系统开始具备基础闭环能力。

## 18. 当前版本的局限与注意点

虽然这一版结构已经明显成熟，但仍有一些局限需要明确。

### 18.1 偏航角是纯积分，长期会漂移

当前 `yawDeg` 来自陀螺仪积分，没有与磁力计或其他姿态源融合。

因此：

- 短时修正有效
- 长时绝对角度会漂移

不过对当前避障场景来说，这仍然是合理折中。

### 18.2 扫描决策策略仍较简单

当前优先级固定为：

- 右 -> 中 -> 左 -> 后退

这意味着它更像一个规则型避障器，而不是最优路径规划器。

### 18.3 测距为 0 时仍按“大距离”归一化

`normalizeDistanceCm()` 会把无效值映射为较大安全值。

优点是流程简单；
缺点是若超声波丢回波频繁，可能导致对空旷程度过于乐观。

### 18.4 转向采用定时控制而非角度闭环

当前 `AVOID_TURN_LEFT/RIGHT` 使用固定时间转向，而不是转到某个目标角度。

因此：

- 实现简单
- 但实际转过的角度会受地面摩擦、电池电压、载荷影响

## 19. 当前实现的工程定位

如果用一句话描述当前 `src/main.cpp`：

> **它是一个基于任务调度、具备多方向扫描避障与短时偏航闭环修正的两轮差速机器人底盘控制程序。**

它已经完成了一个较完整的最小自主闭环：

1. 感知环境
2. 判断前方是否受阻
3. 扫描左右中方向
4. 选择动作
5. 执行动作
6. 在直线动作中进行偏航修正
7. 输出灯光与串口反馈

从课程作业或阶段验收的角度看，这已经比单纯“能跑起来”的版本更有结构价值。

## 20. 与历史参考代码 `lib/srcv4` 的关系

`lib/srcv4/` 中的旧代码仍然很有参考价值，尤其体现在：

- 原始多模式设计
- 成熟的小车功能集合
- 传感器与驱动组合经验

但当前 `src/main.cpp` 走的是另一条更清晰的路线：

- 用任务调度替代“大 loop”
- 用共享状态替代分散变量
- 用动作抽象替代到处写电机控制
- 用显式避障阶段替代单层条件判断

所以二者关系更适合描述为：

> **旧版本提供成熟功能经验，当前版本提供新的主线架构。**

## 22. 总结

当前项目已经不再只是一个“超声波测距控制小车”的简单例程，而是形成了比较明确的工程结构：

- 用 `TaskScheduler` 管理周期任务
- 用 `RobotState` 保存运行上下文
- 用 `MotionCommand` 抽象两轮差速动作
- 用 `AvoidancePhase` 管理避障状态机
- 用 MPU6050 做前进/后退过程中的偏航修正
- 用 WS2812 和串口做实时反馈

因此，当前最值得关注、也是最能代表项目主线水平的文件仍然是：

- `src/main.cpp`

如果把这一版放在开发阶段里定位，最准确的说法是：

> **WALL-E 当前 Uno 主控程序已经进入“结构化避障控制版本”，并具备了基础闭环运动控制能力。**
